| 1 | major | §6.3 drop scan step 2-3 (multiset key `typeId\|amount\|name`); Q4 | Bedrock merges nearby item entities of the same type into one entity up to the max stack size (and splits nothing back). If the bot's inventory held, say, cobblestone 40 in slot 1 and 40 in slot 5, a disconnect drops two item entities that merge to 64 + 16 on the ground. The exact `type\|amount` match then finds neither 40, nothing is skipped, and the restore writes 80 cobblestone while 80 lie on the ground: a **duplicate**, which breaks the "never duplicates" rule (Q4 claims the scan can only lose or leave items, never duplicate). | Replace the matching rule of §6.3 steps 2-3 by an aggregate rule. Step 2: build a map `ground: Map<string, number>` keyed `typeId\|name-or-empty` with the **sum of `itemStack.amount`** over valid item entities (non-stackable stacks, `maxAmount === 1`, are keyed `typeId\|name\|1` and counted as one each). Step 3: walk the plan steps in order; for a stackable step with key `k` and `g = ground.get(k) ?? 0`: if `g >= step.n` then skip the step and `ground.set(k, g - step.n)`; else if `g > 0` then replace the step amount by `step.n - g` (a new field `ApplyStep.nOverride`; `buildStack` uses it) and `ground.set(k, 0)`. `DropScanResult` becomes `{ available: true; skip: SlotKey[]; reduce: Record<SlotKey, number>; matched: number }` and `ApplyCursor` gets `reduce`. Rewrite the example: snapshot cobble 40 (slot 1) + 40 (slot 5), ground one 64 + one 16 entity: ground total 80, both steps skipped. Change Q4 to "stale checkpoints can still skip or double a coincidental stack of the same type; the aggregate rule never restores more of a type than `snapshot total - ground total` when the ground total is within the radius". Add §12-style tests: merged 64+16, partial overlap (ground 30 of a 40 step restores 10). |
| 2 | major | §7 `reloadDropScanRadius` 8; §6.3 step 1-2 centre `snap.lastPos` | After Save & Quit the dropped items lie where the bot stood at quit, not at the last checkpoint position. A checkpoint is up to `intervalTicks` = 200 ticks old (10 s); a sprinting bot covers `0.28 * 200 = 56` blocks in that time, so the items can be up to 56 blocks from `lastPos`. With radius 8 the scan sees nothing, skips nothing, and the restore duplicates every dropped stack (when `dropsOnDisconnect` is true, the default). | Set `reloadDropScanRadius` default to **64** (= ceil(`sprintBlocksPerTick` 0.28 * `intervalTicks` 200) + 8) and define it in the table as "`ceil(0.28 * max(intervalTicks, fallbackIntervalTicks)) + 8`". In §6.3 step 1 replace the single `isChunkLoaded(lastPos)` test by: the chunk at `lastPos` AND the four points `lastPos ± radius` on x and z must all be loaded, else `{ available: false }` (the scan must never run on a partly loaded area, because unloaded chunks hide dropped items). Add to §8 a question Q10: "A 64-block scan can match unrelated stacks of the same type; accepted, the aggregate rule of finding 1 limits the damage to skipping at most `ground total` items, which stay on the ground (conserved)". |
| 3 | minor | §5.5 step 3 (`addEnchantments` with the full list in one try) | `addEnchantments` throws `EnchantmentTypeNotCompatibleError` or `EnchantmentLevelOutOfBoundsError` and applies nothing if any single enchantment is rejected (d.ts S:15690-15705: "thrown if any enchantment is not compatible"). Items from commands or old worlds can carry an enchantment the engine now rejects; the whole enchant set (for example Mending, Unbreaking III, Protection IV on a chestplate) is silently lost on Save & Quit restore, although the item value in S2a assumes it. | Replace step 3 by: "for each `[id, level]` in `ench` order: skip unknown ids; `try { enchantable.addEnchantment({ type: new EnchantmentType(id), level }) } catch { log '[colony] enchant skipped <id> on <type>'; count skipped }`" (`addEnchantment` single, S:15679). Log the number of skipped enchantments once per restore. Add a test: an item with one incompatible enchantment keeps the other two. |
| 4 | minor | §2 `EXCLUDED_EXACT` | Items whose Bedrock data is not exposed by the API and that are missing from the list would be serialized as the plain item and silently degraded across Save & Quit: mob buckets (axolotl colour/variant, tropical fish pattern and colours), `decorated_pot` (sherds), `bee_nest` and `beehive` (bees inside). Armour trims are already covered as an invisible loss. | Add to `EXCLUDED_EXACT`: `"minecraft:axolotl_bucket", "minecraft:cod_bucket", "minecraft:salmon_bucket", "minecraft:pufferfish_bucket", "minecraft:tropical_fish_bucket", "minecraft:tadpole_bucket", "minecraft:decorated_pot", "minecraft:bee_nest", "minecraft:beehive"`. | 5 | minor | §5.4 step 2 equipment/inventory restore; §5.1 | Bedrock gives a respawned/new SimulatedPlayer an empty inventory, but a bot that has just been spawned next to dropped items may pick up an item entity (including its own dropped stacks from a Save & Quit) within the first ticks, before `applySnapshot` runs (it waits for two grounded pumps, >= 4 ticks). The picked-up stack then sits in a slot the plan wants to write, and the "never overwrite, relocate to an empty slot" rule moves the snapshot stack: both copies exist (duplicate) when the scan had already skipped nothing. | In §5.3 step 2 add a precondition the caller (S4b) must meet and S4a checks: "before the first write, `applySnapshot` reads `inv.emptySlotsCount`; if it is not 36 (the body already holds items) and `snap.status === 'online'` and `opts.scanDrops`, the drop scan is repeated **after** that read, and the picked-up stacks are subtracted from the aggregate ground map as if they were still on the ground (`ground[k] += pickedUpAmount`)". Simpler equivalent fix (preferred): S4b keeps a freshly spawned restore bot from picking items up by spawning it at the destination and applying within the same pump, and §5.3 adds "the first read of `inv` happens before any other await/pump; if `emptySlotsCount !== 36` the attempt returns `refused not_ready` once and retries after `applyRetryTicks`, and after the second try proceeds with the aggregate rule above". Pick the preferred fix and record it in Q4. |
