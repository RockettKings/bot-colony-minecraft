# Review: API-MAP — precision
Skipped as already decided: D8 (`EntityItemComponent.itemStack` row), D20 (`minecraft:breathable` row; sharpness; honey_bottle), D18 (probe P15), D17.

| # | Severity | Location | Problem | Exact fix |
|---|---|---|---|---|
| 1 | blocker | §F "Dynamic property" design: "write the new chunks, then the count, then delete stale chunks, so a crash part-way never corrupts the last good snapshot" | Contradiction. The keys are `colony:snap:<botName>` + `…:0`, `…:1` (fixed names). Writing "new chunks" to the same keys overwrites the last good chunks in place. A crash after chunk 0 is written leaves new chunk 0 + old chunk 1 under the old count: a corrupt snapshot. The stated guarantee does not hold. | Replace the design bullet with: "Keys: `colony:snap:<lowercaseName>:ptr` holds the JSON `{ "gen": <int>, "parts": <int> }`; chunk `i` of generation `g` is stored at `colony:snap:<lowercaseName>:<g>:<i>`. Write order: (1) write all chunks of generation `gen+1`; (2) read them back and compare lengths; (3) write `:ptr` with the new `gen` and `parts`; (4) delete the chunks of the old generation. A reader only trusts the chunks named by `:ptr`. S4a's key names must match this scheme." |
| 2 | major | §A5 "Fallback proxy" | The proxy uses unspecified numbers and differs from S1 §5.4/§5.3: "in the last N ticks" (N undefined), "within 16 blocks", "fell over the last ~20 ticks", "families includes `monster`". S1 uses `provokeMemoryTicks`, `approachRadius` (6), `approachMinDelta` (0.3 blocks) and a 20-tick window, and requires `classification === "threat"`. A builder following API-MAP gets different behaviour. Same "N ticks" appears in the "Impossible" table row "Mob target query". | Replace the three bullets with: "`mob_aggroed_on_bot` is true if (a) `target?.id === bot.id`, OR (b) this mob hurt or hit the bot within `config.combat.provokeMemoryTicks`, OR (c) the mob is classified `threat`, its distance is <= `config.combat.approachRadius` and the distance fell by >= `config.combat.approachMinDelta` since the previous scan, at most 20 ticks earlier. The numbers live only in S1 §10; this row must not repeat them." Replace "within N ticks" in the Impossible table with "within `provokeMemoryTicks`". |
| 3 | major | §D5 "Rule for the snapshot code" | "any component or data the serializer doesn't understand" is not testable: the set of understood components is not listed. A builder cannot decide `lossy`. | Add: "The serializer understands exactly these component ids: `minecraft:durability`, `minecraft:enchantable`, `minecraft:dyeable`, `minecraft:potion`, `minecraft:book`, `minecraft:inventory` (bundle), plus `typeId`, `amount`, `nameTag`, lore, `keepOnDeath`, `lockMode`, canDestroy, canPlaceOn and dynamic properties. `lossy = true` if the type id is in the NO list of the table above, or if the stack has any other item component outside that list, ignoring `minecraft:food` and `minecraft:cooldown` (both derived from the type)." | 5 | major | §F "Size limit" and §P12 | (a) The unit is undefined: the limit may count bytes, and non-ASCII characters can take 2-4 bytes, so "30,000 characters" may exceed it. (b) P12 tests only 31,000 and 40,000 chars: if 31,000 throws, nothing says what the real limit is, so the "<= 30,000" design is unverified. S6 P1-f tests 1000..10000+ sizes, so the two docs disagree. | Add to §F: "Chunk size is in UTF-16 characters of a JSON string that contains only ASCII (the serializer escapes every char > 0x7E as `\uXXXX`), so characters equal bytes." Replace the P12 "What to do" with: "Write and read back strings of 1,000, 5,000, 10,000, 20,000, 30,000, 31,000 and 40,000 ASCII chars; record the largest size that round-trips. Chunk size = `max(1000, floor(0.9 * largest) / 1000 * 1000)` (as S6 `judgePropSize`)." |
| 6 | major | §D3 equip swap, step 4 | The failure path is incomplete: after `inv.setItem(i, item)` the text says `eq.setEquipment(S, prev)` but not what happens if that also throws or returns `false`. Also on step 3 `ok === false` the equipment slot may be unchanged (so step 4's re-set is redundant) or changed (needed): unknown. | Replace step 4 with: "If step 3 throws or returns `false`: (a) `inv.setItem(i, item)`; (b) `cur = eq.getEquipment(S)`; if `cur` is not the same type and amount as `prev`, call `eq.setEquipment(S, prev)`; (c) if (b) throws or returns `false`, log `[colony] equip rollback failed slot=<S>` and return failure with the slot left as found. Items are never duplicated: `item` is only in the inventory, and `prev` only in the equipment slot." |
| 7 | minor | §Safe rule 6(c) "Restore after the bot is valid and on the ground" | "On the ground" is undefined. | Replace with: "Restore only when `bot.isValid` and `bot.isOnGround === true` (S:9523) on two consecutive pumps (>= 4 ticks apart)." |
