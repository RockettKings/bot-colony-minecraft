# Architecture

Minecraft Bedrock behavior pack (Script API, TypeScript). A colony of simulated-player bots takes `!` chat commands and carries them out under survival rules. Everything runs inside the pack on a normal world: Beta APIs on, cheats off, no network, no API keys, no dedicated server, no LLM at runtime.

Status markers: **[built]** exists in `src/`. **[Phase 3 – planned]** is specified in `docs/PHASE3-SPEC.md` and `docs/phase3/` but not yet implemented.

## 1. Big picture

```
 Player chat "!gather logs 16"                 Minecraft world (engine)
        │                                              ▲
        ▼                                              │ engine calls (adapter only)
 ┌──────────────── src/game  (imperative shell) ───────┴─────────────────────────────┐
 │ frontends/chat.ts, slash.ts   text → Sender + string                                │
 │ runtime.ts   event loop: game happenings → ColonyEvent; Effect → game action        │
 │ bots/        executors (goto, gather), ports, nav, crafting   [built]               │
 │ bots/controller, sensor, combat-executor, body/*              [Phase 3 – planned]   │
 │ snapshot/    store + service (dismiss / rejoin / escape)      [Phase 3 – planned]   │
 │ adapter/     the ONLY code that calls @minecraft/server(-gametest)                  │
 └───────────────┬──────────────────────────────────────────▲──────────────────────────┘
                 │ ColonyEvent (plain data)                  │ Effect[] (plain data)
 ┌───────────────▼──────────── src/core  (functional core, pure TS) ──────────────────┐
 │ commands/   parse text → Command                                                    │
 │ colony/     Colony.handle(event) → Effect[]: bots, tasks, queue, offers, chest      │
 │ items.ts    resource table for !gather                                              │
 │ combat/     sense, brain (scored decisions), stats, mobs/food/values  [P3 planned]  │
 │ snapshot/   codec + flow state machines                               [P3 planned]  │
 │ config.ts   every tunable                                              [P3 planned]  │
 └─────────────────────────────────────────────────────────────────────────────────────┘
```

**The one rule that holds everything together:** `src/core` never imports `@minecraft/*`. `test/boundaries.test.ts` enforces this. Core code is deterministic: time arrives as ticks on events, and randomness comes from an injected `Rng` (Phase 3). That makes every decision unit-testable in Node.

## 2. Layers

### 2.1 Core (`src/core`) [built]
- **`types.ts`:** shared contracts (`Command`, `Task` union, `ColonyEvent`, `Effect`, `ColonySnapshot`, configs). These are owned by the phase architect or contract writer; builders don't change them.
- **`commands/`:** `parse.ts` (grammar), `specs.ts` (usage lines), `help.ts`. Chat text becomes a `Command`, or a parse error with a usage line.
- **`colony/`:** `Colony.handle(event): Effect[]`. It holds the roster, task assignment, the queue, busy-bot offers (`!override` / `!queue`, 30 s expiry), cooldowns and the colony chest. `messages.ts` holds every player-facing string. `allocator.ts` picks bots.
- **`items.ts`:** `RESOURCES` maps each `!gather` key to its source blocks, counted items and tools.

### 2.2 Shell (`src/game`) [built]
- **`runtime.ts`:**
  - Subscribes to chat, slash commands and entity events, then turns them into `ColonyEvent`s.
  - Applies the `Effect`s it gets back: replies, spawns, assigns, cancels, chest lookups.
  - Pumps every executor every **4 ticks**.
- **`bots/executor.ts`:**
  - The `TaskExecutor` contract has `step(now)`, `cancel()` and `progress()`. Phase 3 adds `pause(now)` and `resume(now)`.
  - `ExecutorRegistry` has one factory per `Task` kind. Adding a kind without a factory is a compile error.
- **`bots/goto-executor.ts`, `gather-executor.ts`:** state machines over the engine-free **ports** in `bots/ports.ts` (`BotBody`, `WorkerBody`, `WorldPort`). `gather-logic.ts`, `crafting.ts` and `executor-logic.ts` are their pure helpers.
- **`adapter/`:** implements the ports over the real engine. Every call is wrapped in try/catch and logged with a `[colony]` tag. It is the only importer of `@minecraft/server-gametest`, apart from `src/probes` and `src/gametests`.
- **`frontends/`:** the `!` chat hook (`world.beforeEvents.chatSend`) and the `/colony:c` slash-command fallback.

### 2.3 Probes and GameTests
- **`src/probes/`:** `/colony:probe <name>` runs an in-game experiment that answers an engine question (spawn, chat, chunks, reload). Each prints `[probe] <name>: RESULT PASS|FAIL|INCONCLUSIVE`. Phase 3 adds combat probes in `src/probes/combat/`.
- **`src/gametests/`:** `/gametest runset colony` on a cheats-on dev world. Structures are generated by `scripts/make-structure.mjs` as little-endian NBT `.mcstructure`, with `index = x*sy*sz + y*sz + z`.

### 2.4 Build
`scripts/build.mjs` regenerates the structures, bundles `src/main.ts` with esbuild into `packs/BP/scripts/main.js` (ES2020, `@minecraft/*` external), and with `--pack` zips `packs/BP` into `dist/bot-colony.mcpack`.

## 3. Key flows [built]

**A command:**
1. Chat `!gather logs 16` → `frontends/chat` → `runtime.submitText`.
2. `parse` produces `Command{gather}`.
3. `Colony.handle({kind:"command"})` returns `[reply, assign(bot, GatherTask)]`.
4. The runtime creates an executor from the registry.
5. Every 4 ticks the runtime calls `step(now)`. When progress changes it sends `taskProgress`. On a terminal result it sends `taskReport`, and the core replies to the player.

**Busy bots:** if every bot is busy for another player, the core stores an offer. The other player's `!override` preempts the task, which is requeued with its progress, while `!queue` waits.

## 4. Phase 3 design (combat-first) [planned]

Specified in `docs/PHASE3-SPEC.md` (index, vocabulary, jobs) and the section files in `docs/phase3/spec/`. Data sources are in `docs/phase3/`: `API-MAP.md` (verified engine calls), `MOBS.md` (mob knowledge base) and `TABLES.md` (food and item values).

- **Every bot is a combat bot first.** A per-bot `BotController` runs a priority stack each pump: **reflex → combat → task → idle**.
  - A threat **pauses** the task executor; it **resumes** afterwards with progress kept.
  - The core still sees the task as active.
- **Sense → decide → act:**
  - **Sense:** `sensor.ts` builds a `Percept` (plain data).
  - **Decide:** the pure `combat/brain.decide(percept, brainState, kb, cfg)` returns a `Decision`. Options are attack, shield, back off, retreat, eat, flee, escape_rejoin, resume_task or idle. Each is scored, with hysteresis.
  - **Act:** `combat-executor` runs the chosen tactic through the `BodyActions` port.
- **Objective relevance, not stances.** Each mob is classified as threatening_me, blocking_objective or irrelevant. Irrelevant mobs are never chased (leash distance).
- **Never attack players,** villagers, golems or tamed pets. Every attack goes through one guarded `attackTarget` call that enforces reach and line of sight, because `attackEntity` itself ignores both.
- **Knowledge base:** per-mob danger, tactics and DO/DON'T rules (`MOBS.md` → `combat/mobs.ts`). Outcome stats per mob × tactic drive the tactic choice and feed Phase 8's learned policy.
- **Snapshot system**, the one approved survival-rule exception:
  - The bot's inventory and equipment are serialized into world dynamic properties, cleared, then restored exactly once when it respawns.
  - It powers escape at low HP (home if set, else the owner's feet; no cooldown), `!summon`, `!dismiss`, idle self-dismiss, and surviving Save & Quit.
  - Snapshots are written on inventory change and on a timer, because the shutdown event can't save.
- **New commands:** `!defend [radius]`, `!home set`, `!summon`, `!dismiss`, `!recall`, and a richer `!status`.

## 5. Survival rules (what bots may and may not do)
- **Forbidden for gameplay:** `/give`, `/tp`, `/fill`, setBlock, item spawning. Bots break, place, pick up and craft like players.
- **Allowed abstractions:** container transfer when standing next to the container; crafting that consumes the exact ingredients; equipment moves between owned items.
- **The one exception:** snapshot restore (Phase 3), exactly once per snapshot and never duplicating.
